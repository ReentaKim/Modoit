## 3. 검증 방법
v0.2와 같습니다. 실제 App·EditorPane·StickyApp·TipTap을 jsdom에서 띄우고 가짜 백엔드에 붙이며, Rust 하네스는 `#[path]`로 소스를 수정 없이 불러옵니다. 이번에 더한 것은 다음과 같습니다.
- **토글 교차 검증**: 37개 말뭉치를 실제 편집기로 왕복했습니다.
  - 편집 가능 판정, 문서 구조, 태그 수를 원문과 비교했습니다.
  - 앱 안에서 만든 문서(JSON → 저장 → 다시 열기) 6종도 돌렸습니다.
- **병합 무작위 시험**: base·mine·theirs를 무작위로 만들어 3,000건을 돌렸습니다.
  - 한쪽만 넣거나 고친 줄이 결과에 있는지 셌습니다.
  - 양쪽이 모두 남긴 base 줄이 결과에 있는지 셌습니다.
- **대비 계산**: CSS 토큰 값으로 WCAG 대비비 98쌍을 계산했습니다(`scratchpad/qa-v03/contrast.py`).
  - 본문·링크·선택 행·체크 표시·버튼, 강조 8색 × 라이트·다크, 스티키 5색 × 라이트·다크
- **생성 시각**: 실제 APFS 임시 폴더에서 `created()`를 비교했습니다(Rust 하네스 qa_r7).
- **v0.2 회귀**: v0.2 Rust 하네스(qa_r1~r6), frontmatter 60개, 이미지 링크 60개, 왕복 말뭉치 120개를 현재 코드로 다시 돌렸습니다.

> 예상 실패 14건은 모두 `it.fails`를 `it`으로 바꿔 따로 돌려, 의도한 단언에서 실패하는 것(다른 예외가 아님)을 확인했습니다.

### 7.2 상세

#### BUG-39 병합 저장 도중 입력하면 상대 창의 줄이 사라진다
- **심각도**: 보통(조용한 데이터 손실, 발생 빈도 낮음) · **확신**: 확인됨(S: `v03Session.test.ts` BUG-39) · **관련**: BUG-26, ADR-12
- **재현 절차(메커니즘)**
  1. 같은 메모를 메인과 스티키에 연다. 스티키에서 한 줄을 써서 저장한다
  2. 메인에서 입력하고 0.5초 뒤 저장이 시작되는 순간(디스크 읽기·쓰기 대기 중)에 이어서 친다
- **기대 결과**: 스티키 줄과 메인의 모든 입력이 남는다
- **실제 결과**
  - 첫 저장은 병합본(스티키 줄 포함)을 쓰고 `saved = 병합본`이 된다.
  - 그사이 새 입력이 있어 `pending !== body`가 되므로 `onMerged`가 불리지 않는다. 화면은 스티키 줄이 없는 채로 남는다.
  - 다음 저장에서는 디스크가 `saved`와 같으므로 병합 없이 화면 내용으로 덮어쓴다. 스티키 줄이 파일과 양쪽 화면에서 사라진다.
  - 시뮬레이션 결과: `'제목\n\n본문 내1 내2'`(스티키 줄 없음)
- **근거 코드**: `noteSession.ts:89-92`(`saved = written`, `pending === body`일 때만 onMerged), `EditorPane.tsx:66-68`(`!s.dirty`일 때만 다시 보여 줌)
- **조치 제안**: 병합이 일어났는데 그사이 입력이 있으면, `saved`를 병합 전 base로 두어 다음 저장에서 다시 병합되게 한다. 또는 남은 입력(pending)을 병합본 기준으로 한 번 더 병합한다

#### BUG-40 저장할 수 없는 세션이 영원히 남는다
- **심각도**: 보통 · **확신**: 확인됨(S: `v03Session.test.ts`, `v03App.test.tsx` BUG-40) · **관련**: BUG-24, BUG-22, NFR-13
- **재현 절차**
  1. 메모 A를 연 채 Finder에서 A를 다른 폴더로 옮기거나 지운다(iCloud 동기화로 사라져도 같다)
  2. A에 글을 친다 → "저장하지 못했습니다" 알림이 뜬다
  3. 메모 B로 넘어간다
  4. 몇 분 뒤 "저장 폴더 변경"을 한다
- **기대 결과**: 입력이 어딘가(원래 자리 다시 만들기, 새 메모, 클립보드 등)에 살아남거나 사용자가 정리할 수 있다. 재시도는 끝이 있다
- **실제 결과**
  - 세션이 `released` 상태로 3초마다 영원히 다시 시도한다. `read_note`가 계속 "No such file"로 실패한다.
  - 입력은 어디에도 저장되지 않는다.
  - `unsavedCount() > 0`이 계속되어 저장 폴더 변경이 "저장하지 못한 메모가 있어…"로 재시작 전까지 막힌다.
  - 목록의 우클릭 "휴지통으로 이동"(`App.tsx:247-263`)으로 지운 메모도, 그 세션이 실패 중이면 같은 상태가 된다. 그 경로는 세션을 취소하지 않는다.
- **근거 코드**: `noteSession.ts:101-104`(실패 원인을 구분하지 않고 재시도), `noteSession.ts:125-135`(release), `App.tsx:49`(폴더 변경 차단)
- **비고**: v0.2에서는 이 경우 입력이 전환 즉시 사라졌습니다(BUG-24). 지금은 사라지지는 않지만 살릴 방법도 없고, 대신 앱 기능 하나가 막힙니다

#### BUG-41 토글 안 코드의 `</details>`가 토글을 깨뜨린다
- **심각도**: 보통(앱이 쓴 내용으로 생기는 데이터 훼손, 쓰임새는 드묾) · **확신**: 확인됨(S: `v03Editor.test.tsx` BUG-41 ×2, X-4) · **관련**: FR-48
- **재현 절차**
  1. `> `로 토글을 만들고 내용에 "닫는 태그는 `` `</details>` `` 입니다"를 인라인 코드로 쓴다. HTML 설명 메모가 이런 경우다
  2. 다른 메모로 갔다가 돌아온다
  3. 아무 글자나 친다
- **기대 결과**: 같은 토글이 그대로 열리고 저장된다
- **실제 결과**
  - 다시 열면 토글이 인라인 코드 안의 `</details>`에서 끝난다. 그런데 편집 가능 판정은 통과한다.
  - 첫 해석이 이미 틀렸기 때문에 왕복 비교가 잡지 못한다.
  - 다음 저장 결과는 ``닫는 태그는 \`\n\n</details>\n\n\` 입니다``처럼 내용이 토글 밖으로 흩어지고 역슬래시가 붙는다.
  - 다른 앱의 문서에서 코드 블록 안에 짝 없는 `</details>` 한 줄이 있어도 같다.
- **근거 코드**
  - `toggle.ts:21-32`(`detailsEnd`가 코드 구간을 구분하지 않고 정규식으로 셈)
  - `markdownSafety.ts:84-89`(`stripToggleTags`가 코드 안의 태그 줄도 걷어 냄)

#### BUG-42 메인 창의 0.5초 대체 경로가 저장 못 한 스티키를 닫는다
- **심각도**: 보통 · **확신**: 확인됨(S: `v03App.test.tsx` BUG-42) · **관련**: BUG-24("스티키는 저장 전에는 닫히지 않는다"), BUG-38, FR-44
- **재현 절차**
  1. 스티키에 글을 친다
  2. 그 메모의 저장이 실패 중이거나(BUG-40과 같은 상황), 스티키가 가려져 스크립트가 늦어 아직 저장 전인 상태다
  3. 메인 창에서 ⌘⇧S 또는 "다시 넣기"를 누른다
- **기대 결과**: 저장되지 않은 입력이 있으면 창을 닫지 않고 알린다
- **실제 결과**
  - 스티키는 `close()`에서 `dirty`라 닫기를 멈춘다(`StickyApp.tsx:142-145`).
  - 메인은 0.5초 뒤에도 창이 있으니 `close_sticky_window`로 강제로 닫는다(`App.tsx:138-144`). 창과 함께 입력이 사라진다.
  - 주석은 "스티키는 창을 떠날 때 이미 저장해 둔다"고 가정한다. 그러나 저장 실패 중이거나, 가려진 창에서 blur 처리 자체가 늦으면 이 가정이 깨진다.
- **조치 제안**: 대체 경로로 닫기 전에, 스티키가 응답했는지(예: `sticky-put-back` 응답 이벤트)나 디스크 본문이 마지막 입력과 같은지 확인한다

#### BUG-46 불완전한 `<details>`가 편집 가능으로 열린다
- **심각도**: 낮음 · **확신**: 확인됨(S: `v03Editor.test.tsx` BUG-46 ×4, X-4) · **관련**: FR-48, NFR-14, BUG-29 방침(의미 보존)
- **내용**: 다른 앱에서 온 아래 문서는 읽기 전용이 아니고, 첫 저장 때 이렇게 바뀐다

  | 원문 | 저장 결과 |
  |---|---|

  | `<summary>` 없는 `<details>` | 빈 제목 토글 + 내용은 토글 밖 |

## 8. 결함이 아닌 관찰

#### BUG-47 이스케이프한 백틱이 토글을 가린다
- **재현 절차**
  1. 토글을 만들고 내용에 "it`s"처럼 백틱 하나를 글자로 친다. 닫지 않았으므로 인라인 코드가 되지 않는다
  2. 그 아래 다른 토글이나 문단에도 백틱 하나를 친다
  3. 다른 메모로 갔다가 돌아온다
- **기대 결과**: 같은 토글로 편집 가능하게 열린다
- **실제 결과**
  - 저장 파일은 `it\`s`, `that\`s`처럼 정상이다.
  - 그러나 다시 열 때 `maskCode`가 이스케이프 여부와 문단 경계를 보지 않고 첫 `` \` ``와 둘째 `` \` ``를 하나의 코드 스팬으로 짝짓는다. 그 사이의 `</details>`·`<details>`가 가려진다.
  - 그래서 토글이 인정되지 않아 "HTML" 읽기 전용으로 열린다.
  - "그래도 편집"으로 열면 두 토글이 하나로 합쳐지거나 내용이 토글 밖으로 나온 구조다. 저장하면 그 구조로 굳는다.
  - 토글 제목과 내용에 백틱이 하나씩만 있어도 같다.
- **확인**: S v03Fix BUG-47 ×3(다시 열기 판정 `['HTML']`, 구조 다름)
- **조치 제안**: 백슬래시 바로 뒤의 백틱은 건너뛰고, 코드 스팬은 빈 줄을 넘지 않게 한다(CommonMark 규칙)

#### BUG-48 다시 꺼낸 스티키가 늦은 "다시 넣기"로 닫힌다
- **재현 절차**
  1. 스티키를 메인 창 뒤에 가려지게 둔다
  2. 메인에서 ⌘⇧S(다시 넣기)를 누른다 → 0.5초 안에 응답이 없어 숨겨진다
  3. 곧바로 ⌘⇧S나 목록 우클릭 "스티키로 꺼내기"로 다시 꺼낸다 → 숨긴 창이 다시 보인다
- **기대 결과**: 스티키가 떠 있고 open:true다
- **실제 결과**
  - 스티키 창이 늦게 받은 예전 `sticky-put-back`을 처리한다(받음 응답 → 저장 → open:false → 창 닫기). 방금 다시 꺼낸 창이 사라진다.
  - 시뮬레이션에서는 다시 꺼낸 직후에는 떠 있다가(172행 통과), 늦은 요청이 처리된 뒤 닫혔다(174행 실패).
  - 숨긴 창의 스크립트는 다시 보일 때까지 멈춰 있을 수 있다. 그러면 실제 앱에서는 "다시 꺼내는 순간" 바로 처리되어 더 자주 생길 수 있다(G-15).
- **데이터 영향**: 없음. 스티키는 닫기 전에 저장한다
- **조치 제안**
  - 다시 넣기 요청에 순번(id)을 붙이고, 그 뒤 꺼내기가 있었으면 스티키가 예전 요청을 무시한다.
  - 또는 `open_sticky`가 숨긴 창을 다시 보일 때 "다시 넣기 취소" 이벤트를 보낸다.

- **원인**
  - 스티키는 요청을 받자마자 받음 응답(ack)을 보낸다.
  - 그다음 "0.45초 넘게 늦었고 창이 보이면 사용자가 다시 꺼낸 것"으로 보고 요청을 버린다.
  - 0.5초 전이면 메인은 아직 숨기지 않았으므로 창은 보인다. 그래서 요청이 버려진다.
  - 메인은 ack를 0.5초 안에 받았으므로 스티키가 알아서 닫을 것으로 보고 아무것도 하지 않는다.
- **영향**
  - 데이터 손실은 없다.
  - 사용자가 BUG-38에서 보고한 "넣을 수 없다"와 같은 증상이 좁은 시간 구간에서 다시 생긴다.
  - 다시 누르면 넣어진다.
- **조치 제안**
  - 시간 대신 메인이 실제로 숨겼는지(숨김 순번)로 판단한다.
  - 또는 요청을 버릴 때 ack 대신 "버림" 응답을 보내 메인이 다시 시도하게 한다.
