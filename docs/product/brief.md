## 1. 개요

### 1.1 문제 정의
| # | 문제 | 누가 겪나 | 근거 |
|---|---|---|---|
| P-1 | 스티키를 여러 개 띄우면 앱이 무거워진다 | 할 일을 바탕화면에 여러 장 붙여 두는 사용자 | 스티키 10개에 메모리 1,391 MB (스파이크 측정) |
| P-2 | 한글을 칠 때 가끔 글자가 꼬인다 | 한글 사용자 전부 | BUG-13, BUG-20, G-14(미확인) |
| P-3 | 사이드바·설정·메뉴가 macOS 기본 앱과 미묘하게 다르다 | macOS 사용자 | 웹 화면으로 흉내 낸 컨트롤 |
| P-4 | Dock 종료·로그아웃 때 막 친 글이 사라질 수 있었다 | 전부 | BUG-35 (v0.4에서 수정, v2도 같은 보장 필요) |
| P-5 | Mac App Store에 올릴 수 없다 | 배포 | 비공개 macOS API(`macOSPrivateApi`) 사용 |

**한 문장 정의:** 스티키를 많이 띄우면 무겁고 한글 입력이 불안한 지금 구조를, 같은 기능을 유지한 채 macOS 네이티브로 다시 만든다.

### 1.2 목적 및 배경
- **제품:** Modoit은 Apple 메모의 단정함, 바탕화면 스티키, Notion식 단축 입력, 내 폴더에 저장되는 Markdown 파일을 묶은 macOS 메모 앱이다.
- **경과:** v0.1(MVP) → v0.2(스티키 = 꺼낸 메모, 폴더 계층, 이미지) → v0.3(다크 모드, 토글). 모두 Tauri + React + TipTap 구조다.
- **v2의 목적:** 새 기능이 아니라 **전환**이다. 같은 기능을 더 가볍고, 더 macOS답고, 한글 입력이 안정적인 앱으로 만든다.
- **왜 지금인가:** 스파이크에서 네이티브 스티키가 10개에 152~202 MB(약 1/7)로 측정되어 이득이 확인됐다. 기능이 더 쌓이기 전에 바꾸는 편이 비용이 적다.

### 1.6 사용자 가치
1. **가벼움:** 스티키를 몇 장 띄우든 신경 쓰지 않는다.
2. **믿음:** 어떤 상황에서도 입력이 사라지지 않고, 내 파일을 함부로 바꾸지 않는다.
3. **익숙함:** macOS 기본 앱처럼 보이고 움직인다.
4. **소유:** 메모는 내 폴더의 평범한 `.md` 파일이다. 앱이 없어도 읽힌다.

### 1.7 개발 원칙
1. **파일이 주인이다.** 열기만 해서는 쓰지 않는다. 사용자가 고친 부분만 바꾼다.
2. **입력을 잃지 않는다.** 저장 실패를 숨기지 않는다. 종료·전환·충돌 어느 경우에도 입력을 남긴다.
3. **동작은 v0.3과 같게.** v2.0에서는 새 기능을 넣지 않는다. v0.3 테스트를 명세로 삼는다.
4. **macOS답게, 공개 API만.** 시스템 컨트롤과 단축키를 따르고, 비공개 API를 쓰지 않는다.
5. **규칙은 한곳에.** 제목·파일 이름·frontmatter·경로 검증 규칙은 `ModoitCore` 한곳에만 둔다.

## 2. 기회 및 임팩트 예측

### 2.1 기회
| # | 기회 | 근거 |
|---|---|---|
| O-1 | 스티키 메모리를 약 1/7로 | 스파이크: 스티키 10개 1,391 MB → 152~202 MB |
| O-2 | 한글 입력 문제를 스티키에서부터 해결 | macOS 텍스트 편집기는 한글 조합을 기본으로 처리한다 |
| O-3 | macOS 새 디자인을 자동으로 따른다 | SwiftUI 기본 컨트롤 |
| O-4 | Mac App Store 배포 가능성 | 공개 API만 쓰면 막히는 이유가 사라진다(샌드박스 검토는 별도) |
| O-5 | 앱 크기 축소 | 스파이크 1.4 MB(arm64) vs v0.3 15 MB(universal). 아키텍처가 달라 단순 비교 불가 |

### 2.2 임팩트 예측
| 지표 | v0.3 | v2.0 목표 | 근거 |
|---|---|---|---|
| 스티키 10개 + 메인 창 메모리 | 1,391 MB | **300 MB 이하** | 스파이크 152~202 MB에 여유를 둠 |
| 스티키 1개 추가 비용 | 약 120 MB | **20 MB 이하** | 스파이크 약 5 MB |
| 메인 창만(스티키 0개) 메모리 | 176 MB | **176 MB 이하**(v0.3보다 무거워지지 않음) | 스파이크 142~166 MB |
| 실행 → 준비(스티키 10개) | 측정 못 함 | **1초 이하** | 스파이크 509 ms |
| 한글 입력 결함(G-14 시나리오) | 확인 못 함 | **0건** | — |
| 종료 경로별 입력 유실 | Dock·로그아웃 때 가능 | **0건**(강제 종료 제외) | v0.4 수정 |

**측정 기기:** 모든 수치는 대표 Mac(MacBook Pro, M5 Pro, 24 GB, macOS 26)에서 잰다. 스파이크 수치도 같은 기기다.

표·토글이 있는 메모의 스티키는 TipTap 편집기로 열리므로 1개당 75~100 MB가 든다. 그런 스티키가 많으면 목표 메모리를 넘을 수 있다(리스크 R-6).

### 2.3 예상되는 사용자 행동
- B-1: 스티키를 지금보다 더 많이, 더 오래 띄워 둔다.
- B-2: 스티키에서 직접 입력하는 일이 늘어난다(메인 창을 덜 연다).
- B-3: 앱을 끄지 않고 계속 켜 둔다(가벼워지므로).
- B-4: 표·토글은 주로 메인 창 메모에 쓰고, 스티키는 체크리스트 위주로 쓴다(네이티브 범위와 맞음).

### 2.4 가설 검증 지표
Modoit은 사용 데이터를 수집하거나 전송하지 않는다(3.5). 그래서 검증은 **측정 스크립트와 대표의 사용 기록**으로 한다.

| 가설 | 검증 지표 | 방법 | 판정 기준 |
|---|---|---|---|
| H-1 네이티브 스티키가 메모리 문제를 해결한다 | 스티키 N개 메모리 합계 | `spike/bench.sh`와 같은 방법, 출시 전 측정 | NFR-17 충족 |
| H-2 스티키 대부분은 네이티브로 열린다 | 열린 스티키 중 TipTap으로 열린 비율 | 대표가 v0.4를 실제로 2주 이상 쓴 뒤(2026-11-10 시작), 저장 폴더에서 TipTap 서식(F-08 3.2)이 든 메모 수를 센다(스크립트) | 20% 이하면 설계 유지, 넘으면 네이티브 서식 범위(D-12)를 넓힌다 |
| H-3 한글 입력 결함이 사라진다 | G-14 시나리오 결함 수, 출시 후 4주간 대표 보고 수 | QA 수동 확인, 사용 기록 | 0건 |
| H-4 가벼워지면 스티키를 더 띄운다 (B-1) — **참고 지표** | 동시에 띄운 스티키 수 | 따로 기록하지 않는다. 출시 전후 대표의 체감과 저장 폴더의 `sticky.open` 수를 가끔 본다 | 판정하지 않는다. v2 목적(가벼움)은 H-1로 판정 |

### 3.1 데이터 저장
| # | 규칙 | 이유 |
|---|---|---|
| 1 | 메모는 사용자가 고른 **저장 폴더**에 메모 하나당 `.md` 파일 하나로 저장한다 | 데이터 소유. 앱 없이도 읽힌다 |
| 2 | 앱의 폴더 = 저장 폴더 안의 실제 디렉터리. 가상 폴더·태그는 없다 | Finder와 앱의 구조가 같아야 한다 |
| 3 | 앱 전용 데이터는 `저장폴더/.modoit/`(폴더 순서·구분선), 앱 설정 파일, macOS가 관리하는 앱 상태(창 위치, 마지막 선택 — F-02)에만 둔다 | 메모 파일을 깨끗하게 둔다 |
| 4 | 저장 폴더 밖의 파일을 읽거나 쓰지 않는다. `..`, 절대 경로, 밖을 가리키는 심볼릭 링크는 거부한다. 편집기에 주는 파일도 같다 | 보안 |
| 5 | 쓰기는 원자적으로(임시 파일 → 바꿔 끼우기). 파일 생성 시각은 유지한다 | 쓰는 도중 꺼져도 원본이 깨지지 않는다 |
| 6 | 일부 폴더·파일을 읽지 못해도(권한, UTF-8 아님) 그것만 건너뛰거나 읽기만 막는다 | 일부 문제로 전체를 못 쓰게 하지 않는다 |
| 7 | 제목·파일 이름·frontmatter·경로 검증 규칙은 `ModoitCore` 한곳에서만 계산한다 | 규칙이 두 곳에서 달라지는 결함(BUG-17, 18, 32) 방지 |

### 3.2 저장·충돌·실패
| # | 규칙 | 이유 |
|---|---|---|
| 1 | 입력을 멈추고 **0.5초** 뒤 자동 저장한다. 저장 버튼은 없다 | 저장을 신경 쓰지 않게 |
| 2 | 메모 전환, 창 숨기기·닫기, 다른 창으로 떠날 때는 바로 저장한다 | 두 창을 오갈 때 충돌을 줄인다 |
| 3 | 저장 직전 디스크 내용이 내가 알던 내용과 다르면 **줄 단위 3-way 병합**. 같은 줄 충돌은 **양쪽 모두 남긴다** | 입력을 잃지 않는 것이 깔끔함보다 우선 |
| 4 | 입력 중인 창은 외부 변경으로 덮어쓰지 않는다 | |
| 5 | 실패하면 알리고 **3초마다** 다시 시도한다. 실패한 세션은 메모를 바꿔도 닫지 않는다 | 실패를 숨기지 않는다 |
| 6 | 저장할 때 파일이 없어졌으면 그 자리에 다시 만든다. 앱에서 휴지통으로 보낸 메모는 예외 | 입력을 살린다 |
| 7 | 어떤 종료 경로에서도 저장을 마친 뒤 끝낸다(F-12) | |

### 3.3 삭제는 휴지통으로
| # | 규칙 | 이유 |
|---|---|---|
| 1 | 메모·폴더 삭제는 항상 시스템 휴지통을 거친다 | 복구 가능 |

## 6. FAQ
| 질문 | 답 |
|---|---|
| 왜 다시 만드나요? | 스티키를 많이 띄우면 무겁고 한글 입력이 불안하기 때문이다. 같은 기능을 macOS 네이티브로 만들어 해결한다(1.1) |
| 인터넷이 필요한가요? 웹 앱인가요? | 아니다. 설치형 macOS 앱이며 인터넷 없이 동작한다. 메인 편집기는 macOS에 들어 있는 Safari 엔진으로 **앱 안에서** 그린다. v0.3도 같다 |
| 왜 메인 편집기는 네이티브가 아닌가요? | 표·토글·`/` 메뉴·원본 보존을 갖춘 네이티브 Markdown 편집기가 없다. 직접 만들면 수개월이 걸린다. v2.x에서 다시 판단한다 |
| 스티키는 모두 네이티브인가요? | 아니다. 체크리스트·목록·굵게·제목 같은 서식만 있으면 네이티브, 표·토글이 있으면 TipTap 편집기로 연다. 겉모습은 같다 |
| v0.3에서 쓰던 메모는요? | 같은 저장 폴더를 그대로 연다. 변환하지 않는다. v2에서 저장한 폴더를 v0.3으로 열어도 된다(NFR-16) |
| v0.3과 v2를 동시에 켜도 되나요? | 권하지 않는다. 같은 파일을 두 앱이 고치면 병합은 되지만 스티키 창이 두 벌 뜬다. 전환 안내에 적는다 |
| iOS 앱은요? | 당분간 계획하지 않는다(D-03) |
| Mac App Store에 나오나요? | 아니다. dmg와 Homebrew로 무료 배포한다. 공증·App Store는 비용(개발자 계정) 때문에 하지 않는다(D-11). 처음 열 때 "그래도 열기"가 필요하다 |
