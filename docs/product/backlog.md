## 1. 우선순위 방식
| 대상 | 방식 | 이유 |
|---|---|---|
| 한 버전의 출시 범위 | **MoSCoW** (Must / Should / Could / Won't) | "이번에 꼭 넣을 것"을 정하는 데 맞다. 요구사항 정의서에 적는다 |
| 다음 버전 후보(이 문서) | **RICE** | 후보끼리 순서를 숫자로 비교한다 |
| 결함(BUG-xx) | 심각도(치명·높음·중간·낮음) | 결함은 이득보다 손해(데이터 유실 등)로 판단한다. RICE를 쓰지 않는다 |
| 전략 항목(배포 채널, 플랫폼) | 대표 결정 | 사용 빈도로 잴 수 없다 |

## 2. RICE 기준
**점수 = Reach × Impact × Confidence ÷ Effort**

| 요소 | 의미 | 이 프로젝트에서 재는 법 |
|---|---|---|
| Reach | 얼마나 자주·많이 닿나 | 1차 사용자(대표)가 **한 달에 그 기능을 쓸 횟수** 추정. 사용 데이터를 모으지 않으므로(Brief 3.5) 대표의 판단이 기준이다 |
| Impact | 한 번 쓸 때 얼마나 좋아지나 | 3 매우 큼 / 2 큼 / 1 보통 / 0.5 작음 / 0.25 아주 작음 |
| Confidence | 위 추정을 얼마나 믿나 | 100% 근거 있음(측정·반복 요청) / 80% 요청 있음 / 50% 추측 |
| Effort | 얼마나 드나 | 개발 일수(설계·구현·테스트 포함) 추정 |

## 5. 운영 규칙
- 새 요청·아이디어는 회의록이나 사용자 피드백에서 이 표로 옮기고, 그때 RICE를 매긴다.
- 버전 범위를 정할 때 위에서부터 고르고, 고른 항목은 그 버전의 요구사항 정의서에 MoSCoW로 넣는다.
- 점수는 분기마다, 또는 대표가 Reach를 고칠 때 다시 계산한다.
