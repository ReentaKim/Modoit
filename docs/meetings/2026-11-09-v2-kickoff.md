## 2. 논의 내용

### 2.1 Swift 전환 (안건 1)
- 개발 의견: 체감 이득은 **스티키 여러 개를 띄울 때의 메모리**와 **한글 입력 안정성**에서 가장 크다. 일반 편집 속도는 지금도 문제가 없다.
- 디자인 의견: SwiftUI를 쓰면 사이드바·툴바·설정·메뉴가 진짜 macOS 컨트롤이 되고, OS 새 디자인을 자동으로 따른다.
- 위험: 표·토글·`/` 메뉴·원본 보존을 갖춘 네이티브 Markdown 편집기가 없다. 메인 편집기는 기존 TipTap을 앱 안 WKWebView에 그대로 넣는다(하이브리드).

### 2.2 스파이크 결과 (안건 2)
| 스티키 10개 | v0.3 | v2 웹 스티키 | v2 네이티브 스티키 |
|---|---|---|---|
| 메모리 합계 | 1,391 MB | 906~1,134 MB | 152~202 MB |
| 스티키 1개당 | 약 120 MB | 약 75~100 MB | 약 5 MB |

- 스티키를 웹으로 두면 Swift로 바꿔도 이득이 작다. **네이티브 스티키에서만 큰 이득이 난다.**
- 코어 규칙 테스트 15개를 Swift로 옮겨 통과했다. Swift에서 `\r\n`이 글자 하나로 다뤄지는 점을 발견했다.
- 확인하지 못한 것: 입력 뒤 저장되는 Markdown이 v0.3과 같은지, 한글 입력(G-14).

### 2.3 BUG-35 (안건 3)
- 원인: Dock "종료", 로그아웃, 재시동은 macOS 기본 종료 경로로 온다. tao(Tauri의 창 라이브러리)에 이 요청을 기다리게 하는 부분이 없어서, 0.5초 저장 대기 중이던 입력이 사라질 수 있었다. ⌘Q도 저장이 끝났는지 확인하지 않고 0.7초 뒤 종료했다.
- 수정(v0.4): 모든 종료 경로를 한곳(`quit.rs`)으로 모았다. 모든 창이 저장을 끝냈다고 답하면 종료한다. 저장에 실패한 메모가 있으면 한 번 멈추고 안내하며, 응답하지 않는 창은 최대 4초 기다린다.
- 결과: 자동 테스트 통과(vitest 230, cargo 45). 실제 앱에 종료 신호를 보내 두 창의 저장을 확인한 뒤 0.43초에 종료했다. **사람이 입력 직후 종료하는 실제 상황은 대표가 확인한다.**

### 2.4 "웹 편집기"라는 표현 (안건 5 관련 질문)
- 대표 질문: "우리는 macOS 설치 앱인데 웹 편집기라니?"
- 답: 인터넷이나 웹사이트와는 관계가 없다. macOS에 들어 있는 Safari 엔진(WKWebView)으로 앱 **안에서** 그리는 편집 화면이며, 인터넷 없이 동작한다. v0.3 화면 전체가 이미 이 방식이다. 앞으로 문서에는 "웹 편집기" 대신 **"TipTap 편집기(앱 내장)"**라고 쓴다.

### 2.5 서비스 기획 프로세스 (안건 7)
- 대표 제시: 서비스 기획은 문제 정의 → 요구사항 정의 → 기획 정책 수립 → 기능 정의 → IA·순서도 → 와이어프레임 → 화면설계서 → 운영 정책서·매뉴얼 순서로 한다. 우선순위는 MoSCoW와 RICE를 쓴다. Spec은 7장 구성이다.
- PM 의견: 먼저 만든 Project Spec과 PRD는 대표가 제시한 Spec 구성과 내용이 거의 겹친다. 문서가 둘이면 같은 내용을 두 번 고쳐야 하므로 Spec 하나로 합친다. MoSCoW는 "이번 버전에 넣을 것", RICE는 "다음에 할 것의 순서"로 나눠 쓴다.
- 이 앱의 특성상 일부 항목은 가볍다: 사용 데이터를 모으지 않으므로 가설 검증은 측정 스크립트와 대표의 사용 기록으로 한다. 관계 법령은 오픈소스 라이선스와 상표가 중심이다.
