## 0. 왜 바꾸나
전통적인 서비스 기획은 단계마다 문서를 따로 만든다(문제 정의 → 요구사항 정의서 → 정책서 → 기능 정의서 → IA·순서도 → 와이어프레임 → 화면설계서 → 운영 정책서). 사람이 손으로 쓰던 시절에는 문서 하나가 한 사람의 몫이라 이 구분이 맞았다.

AI가 초안을 쓰는 지금은 **쓰는 비용은 거의 사라졌고, 읽고 판단하고 일관성을 지키는 비용이 남았다.** Modoit v2를 준비하며 실제로 겪은 일이다.

| 겪은 일 | 원인 |
|---|---|
| 요구사항이 PRD v0.1·v0.2·v0.3 세 문서에 흩어져, v2 때 한곳에 다시 모아야 했다 | 버전마다 문서를 복사해 변경분만 적었다 |
| 요구사항 정의서·정책서·기능 정의서가 같은 규칙을 세 번 적었다 | 단계별 문서 구분이 내용 구분과 맞지 않는다 |
| 기능 정의서를 코드와 대조하니 메뉴, 빈 제목 이름, 링크 동작이 틀려 있었다 | 코드에 있는 사실을 문서에 다시 적으면 어긋난다 |
| Project Spec과 PRD가 거의 같아 하나로 합쳤다 | 이름이 다른 같은 문서 |
| 반대로 가장 쓸모 있었던 것: 결정 기록, 수용 기준, ID가 붙은 자동 테스트 | 코드에서 읽을 수 없는 "왜"와 "약속", 그리고 실행되는 명세 |

그래서 모델의 목표는 셋이다.
1. **소통:** 산출물은 사람이 검토하고 결정하는 매개다. 보관용이 아니다.
2. **최소:** 코드·테스트가 말해 주는 것은 문서에 다시 적지 않는다. 한 사실은 한 곳에만 둔다.
3. **버전 관리:** 모든 산출물은 git에 있고, 변경은 diff로 검토하고, 확정은 merge다.

## 1. 원칙
| # | 원칙 | 뜻 |
|---|---|---|
| 1 | **사람은 판단, AI는 초안** | AI가 초안·정리·대조를 하고, 담당자가 검토해 고치고, 결정자가 확정한다 |
| 2 | **문서는 "왜"와 "약속"만** | 의도, 결정과 이유, 수용 기준, 규칙의 이유. 구현 사실(메뉴 목록, API 전체 등)은 코드가 원본이다 |
| 3 | **한 사실은 한 곳** | 다른 문서는 링크로 가리킨다. 같은 규칙을 두 번 적지 않는다 |
| 4 | **살아 있는 문서 + git 버전** | `PRD-v0.1`, `v0.2`처럼 복사하지 않는다. 문서 하나를 계속 고치고, 버전은 git 태그와 릴리스 노트로 남긴다 |
| 5 | **기능 단위로 나눈다** | 단계별 문서(요구사항서·정책서·기능 정의서) 대신 기능마다 카드 하나에 요구사항·규칙·흐름·화면·검증을 모은다. 담당과 리뷰 범위가 기능과 맞는다 |
| 6 | **실행되는 명세를 우선** | 수용 기준은 가능한 한 자동 테스트로 만들고, 테스트 이름에 요구사항 ID를 넣는다. 문서는 테스트를 가리킨다 |
| 7 | **보여 주는 것이 설명보다 낫다** | 와이어프레임과 화면설계서 대신, 눌러 볼 수 있고 번호 설명이 붙은 HTML 프로토타입 하나 |
| 8 | **검토 요청을 맨 위에** | 모든 산출물 첫 부분에 "이번에 봐 줄 것 / 결정할 것"을 둔다. 읽는 사람이 무엇을 해야 하는지 바로 안다 |
| 9 | **원본은 하나, 형식은 필요할 때** | 외부에 요구사항 정의서나 화면설계서 양식이 필요하면 원본(기능 카드·프로토타입)에서 AI로 만들어 낸다. 그 출력물은 고치지 않는다 |

## 2. 필수 산출물
| # | 산출물 | 답하는 질문 | 형태 | 담당(초안 → 검토 → 확정) |
|---|---|---|---|---|
| 1 | **Brief** (제품 사양서·PRD) | 왜, 누구를 위해, 무엇을, 어디까지, 어떻게 성공을 재나 | `product/brief.md` 하나 | AI → PM → 대표 |
| 2 | **결정 기록** | 무엇을 언제 누가 왜 정했나 | `decisions.md` 하나(D-xx), 긴 논의만 `meetings/` | AI(대화에서 추출) → PM → 대표 |
| 3 | **기능 카드** | 이 기능은 무엇을 약속하고, 어떤 규칙으로, 어떻게 동작하나 | `product/features/F-xx-이름.md` 기능마다 하나 | AI → 기획(기능 담당) → PM |
| 4 | **프로토타입** | 어떻게 보이고 무엇을 누르면 어떻게 되나 | `prototype/*.html` (화면 지도 = IA) | AI → 디자인·기획 → PM |
| 5 | **검증** | 정말 약속대로 되나 | 자동 테스트(ID 연결) + `qa/manual-checks.md` + 릴리스별 결과 보고서 | 개발·QA → QA → 대표(출시 승인) |
| 6 | **아키텍처·ADR** | 어떻게 만들고, 구조를 왜 그렇게 정했나 | `dev/architecture.md` + ADR | AI → 개발 → 대표 |
| 7 | **백로그** | 다음에 무엇부터 | `product/backlog.md` (RICE) | AI → PM → 대표 |
| 8 | **릴리스 노트** | 이번 버전에서 무엇이 바뀌었나 | `releases/vX.Y.md` (버전별 스냅샷) | AI(git 기록) → PM |

출시 단계에만: 운영 정책(배포·업데이트·문의·결함 처리)과 사용자 매뉴얼. 사용자에게 보이는 글이므로 그때 쓴다.

### 2.1 전통 산출물과의 대응
담당자들이 익숙한 이름으로 찾을 수 있게 둔다.

| 전통 산출물 | 이 모델에서 있는 곳 |
|---|---|
| 문제 정의, 목적·배경, 사용자, 유저 스토리·저니맵, 사용자 가치, 개발 원칙 | Brief 1장 |
| 기회·임팩트 예측, 가설 검증 지표 | Brief 2장 |
| 요구사항 정의서 | 기능 카드 "요구사항" + Brief의 비기능 요구사항. 전체 목록은 필요할 때 AI로 뽑는다 |
| 정책서 | 기능 카드 "규칙"(기능별) + Brief의 공통 원칙(여러 기능에 걸친 것) |
| 기능 정의서 | 기능 카드 "동작" |
| 순서도 | 기능 카드 안의 Mermaid 흐름 |
| IA | 프로토타입의 화면 지도 |
| 와이어프레임, 화면설계서 | 프로토타입(번호 설명 포함) |
| 회의록 | 결정 기록. 긴 논의만 회의록 |
| 테스트 계획서 | 자동 테스트 + 수동 확인 목록 |
| PRD v0.1·v0.2·v0.3 | Brief 하나 + git 기록 + 릴리스 노트 |

## 3. 협업 방식

### 3.1 상태와 검토
| 상태 | 뜻 | 누가 바꾸나 |
|---|---|---|
| 초안 | AI나 담당자가 썼다. 아직 아무도 확인하지 않았다 | 작성자 |
| 검토 중 | 담당자에게 검토를 요청했다. 맨 위 "검토 요청"에 볼 것을 적었다 | 작성자 |
| 확정 | 결정자가 승인했다. 바꾸려면 다시 검토를 거친다 | 결정자 |

### 3.2 변경 단위
- **브랜치:** `main` = 출시된 상태(태그), `develop` = 다음 버전 작업. 출시 때만 `develop`을 `main`에 합친다([D-19](decisions.md)).
- **한 변경 = 한 브랜치(PR).** `develop`에서 따고 `develop`에 합친다. 한 결정이나 한 기능 변경을 하나로 묶는다. 문서와 코드가 함께 바뀌면 같은 PR에 넣는다.
- 리뷰어는 diff로 본다. **merge가 확정이다.** 문서 상태를 따로 고치는 일을 줄인다.
- 버전 출시 = `develop` → `main` 합치기 + git 태그 + 릴리스 노트. 그 시점의 모든 문서는 태그로 다시 볼 수 있다.

### 3.3 역할과 AI
| 역할 | AI에게 맡기는 것 | 사람이 하는 것 |
|---|---|---|
| 대표 | 미결 사항 정리, 선택지와 추천 | 결정, 수동 확인, 출시 승인 |
| PM | Brief·결정 기록·릴리스 노트 초안, 문서 간 대조 | 범위·우선순위 판단, 검토 요청 관리 |
| 기획 | 기능 카드 초안, 코드와의 대조, 흐름도 | 규칙의 이유와 예외 판단, 사용자 관점 검토 |
| 디자인 | 프로토타입 초안, 토큰 정리 | 시각·상호작용 판단, 프로토타입 수정 |
| 개발 | 구현, 테스트, ADR 초안 | 구조 판단, 코드 리뷰 |
| QA | 테스트 작성·실행, 결함 재현 | 독립 검증 관점, 수동 확인, 출시 판단 근거 |

### 3.4 AI가 매번 하는 점검
문서 일관성은 사람이 지키기 어렵다. 변경마다 확인한다.

**스크립트가 잡는 것** — `python3 scripts/check-docs.py` (문서를 고친 뒤, 커밋 전에 돌린다. 오류 0건이어야 한다)
- 깨진 링크, 없는 ID(D·FR·NFR·F·SCR·B)를 가리키는 참조
- Must 요구사항마다 검증이 연결되어 있는지, 검증이 가리키는 테스트 파일·이름이 코드에 있는지
- Brief 4.1의 카드별 요구사항 목록·개수·합계가 기능 카드와 같은지
- Brief와 기능 카드에 상태가 적혀 있는지
- 경고: 아직 작성하지 않은 테스트("신규 작성 필요") 목록

**AI가 읽고 판단하는 것** (스크립트로 잡기 어렵다)
- 기능 카드의 사실이 코드와 맞는지(메뉴, 단축키, 기본값 등)
- 같은 규칙이 두 곳에 적혀 있지 않은지

## 4. 디렉터리
```
docs/
  README.md              문서 지도 (어디에 무엇이 있나)
  operating-model.md     이 문서
  decisions.md           결정 기록 D-xx
  meetings/              긴 논의만
  product/
    brief.md             제품 사양서 (PRD)
    features/F-xx-*.md   기능 카드
    backlog.md           RICE
  prototype/             HTML 프로토타입 (index.html = 화면 지도)
  dev/                   아키텍처, ADR
  qa/                    수동 확인 목록, 릴리스별 결과 보고서
  releases/              릴리스 노트, (출시 때) 운영 정책·매뉴얼
  archive/v0.x/          이 모델 이전 문서 (고치지 않음)
```

## 5. 옮긴 순서 (2026-11-09)
1. v0.x 문서를 `archive/v0.x/`로 옮긴다(git 기록 유지, 내용은 고치지 않음).
2. v2 Spec → `product/brief.md`. 회의록의 결정 → `decisions.md`.
3. 요구사항 정의서·정책서·기능 정의서·IA·순서도 → 기능 카드 F-01~F-12와 Brief의 비기능·공통 원칙으로 나눠 옮긴다. 옮긴 뒤 세 문서는 지운다.
4. 프로토타입(HTML)을 만든다. 화면 지도가 IA를 대신한다.
5. 저장소 루트에 `CLAUDE.md`를 두어 어느 AI 에이전트든 이 모델을 따르게 한다.
6. 일관성 점검 스크립트를 만든다. → `scripts/check-docs.py` (2026-11-10)
