## 2. 실행 환경
- macOS 26.6.2 (25G83), Node v24.18.0, rustc 1.99.1
- Tauri 2.12.5, React 19.3.1, TipTap 3.33.0, vitest 5.1.0 + jsdom 31.0.0
- 저장 폴더용 파일 시스템: APFS(대소문자 구분 없음)
- 실행 중인 dev 앱과 `config.json`은 건드리지 않았습니다. 앱 소스도 수정하지 않았습니다.

## 3. 검증 방법
1. **기존 자동 테스트**: `npx vitest run`, `cargo test --lib`, `npx tsc --noEmit`
2. **정적 검증**: FR마다 UI 이벤트 → React 상태 → `invoke` → Rust 명령 → 파일 시스템까지 따라가며 확인했습니다.
3. **Rust 하네스(QA-R)**: scratchpad에 만든 별도 크레이트가 `#[path]`로 `src-tauri/src/vault.rs`를 **수정 없이** 불러옵니다. 임시 폴더(APFS)에서 실제 파일을 만들어 돌렸습니다.
4. **시뮬레이션(QA-S, QA-K)**: 실제 `App.tsx`, `EditorPane.tsx`, `StickyApp.tsx` 코드에 가짜 Rust 백엔드(메모리 파일 시스템, IPC 지연 2ms)를 붙였습니다. TipTap 편집기만 `onChange`를 직접 부르는 가짜로 바꿨습니다. 저장·이름 변경·삭제·외부 변경의 순서 문제를 jsdom에서 재현하는 용도입니다.
5. **편집기 검증(QA-T)**: 실제 `buildExtensions()`로 만든 TipTap 편집기에서 단축 입력, Tab, Markdown 직렬화를 확인했습니다.

> 시뮬레이션은 Tauri IPC와 WebKit을 흉내 낸 것이라 실제 앱과 타이밍이 다를 수 있습니다. 그래서 시뮬레이션으로 재현한 결함도 수정 후 수동 TC로 한 번 더 확인해야 합니다.

### BUG-01 다른 앱에서 만든 Markdown이 첫 편집 때 훼손된다
- **심각도**: 높음 · **확신**: 확인됨(QA-T5) · **관련**: NFR-01, NFR-02, FR-07
- **재현 절차**
  1. 저장 폴더에 아래 내용의 `외부.md`를 다른 편집기로 만든다(Obsidian 볼트를 저장 폴더로 고른 경우와 같다)
     ```markdown
     ---
     tags: [a, b]
     ---
     # 제목

     | a | b |
     |---|---|
     | 1 | 2 |

     ![그림](a.png)
     ```
  2. Modoit에서 열고 아무 곳에나 글자 하나를 친 뒤 0.5초 기다린다
- **기대 결과**: 앱이 지원하지 않는 요소도 파일에 그대로 남는다. 최소한 편집 전에 경고하거나 읽기 전용으로 연다
- **실제 결과**: 파일 전체가 TipTap 직렬화 결과로 덮어써진다. frontmatter는 `---` + `## tags: \[a, b\]`(구분선과 제목)가 되고, 표는 한 줄 문단 `| a | b | |---|---| | 1 | 2 |`, 이미지는 alt 글자 `그림`만 남는다. `<div>`가 사라지고 `[[위키]]`, `snake_case`에는 역슬래시가 들어간다. 백업이 없어 되돌릴 수 없다
- **근거 코드**: `src/editor/extensions.ts:59-73`(표·이미지·frontmatter 확장 없음), `src/editor/ModoitEditor.tsx:30`(편집할 때마다 문서 전체를 `getMarkdown()`), `src/app/EditorPane.tsx:133-140`, `EditorPane.tsx:49`(그 결과로 파일 전체를 덮어씀)
- **비고**: PRD는 표·첨부를 "지원하지 않음"(비목표)으로 정했지만, 이미 있는 내용을 지우는 것은 데이터 안전(NFR-02) 문제입니다. 1차 사용자가 기존 메모 폴더를 고를 가능성이 높아 "높음"으로 분류했습니다

### BUG-02 제목 수정 후 0.5초 안에 다른 메모로 가면 선택이 되돌아간다
- **심각도**: 높음 · **확신**: 확인됨(QA-S1, QA-S2) · **관련**: FR-06, FR-07, FR-08
- **재현 절차 A (클릭)**
  1. ⌘N으로 새 메모를 만들고 "장보기"를 친다
  2. 0.5초가 지나기 전에 목록의 다른 메모 "다른"을 누른다
- **재현 절차 B (⌘N)**
  1. 기존 메모의 첫 줄을 고친다
  2. 0.5초가 지나기 전에 ⌘N을 누른다
- **기대 결과**: A는 "다른"이 열린다. B는 새 빈 메모가 열리고 커서가 들어간다
- **실제 결과**: A는 잠깐 "다른"이 열렸다가 "장보기"로 되돌아간다. B는 새 메모가 만들어졌다가 곧바로 휴지통으로 가고, 고치던 메모가 다시 선택된다. 사용자가 보기에는 클릭이나 ⌘N이 무시된다. 실행 타이밍에 따라 선택된 행과 편집기 내용이 잠깐 서로 다른 메모를 가리키는 상태도 관찰됐다(QA-S1, act를 나누지 않은 첫 실행)
- **원인**: 메모 전환 effect가 이전 메모를 `flush()`하는데, `flush()`는 제목이 바뀌었으면 이름을 바꾸고 `onRenamed(np)`를 부른다. 이때 `pathRef.current`가 아직 이전 메모라 조건을 통과하고, App의 `onRenamed`가 `setSelected(np)`로 선택을 이전 메모로 되돌린다. 전환 중인지 확인하는 조건이 없다
- **근거 코드**: `src/app/EditorPane.tsx:53-58`(`pathRef.current === p`이면 `onRenamed`), `EditorPane.tsx:77-96`(전환 effect가 `await flush()` 뒤에 `pathRef.current = path`), `src/app/App.tsx:184-188`(`setSelected(p)`)
- **비고**: 새 메모를 만들고 제목만 빨리 친 뒤 바로 다음 메모로 넘어가는 흔한 흐름에서 생깁니다

### BUG-03 `&`, `<`, `>`가 든 제목이 HTML 엔티티 파일 이름이 된다
- **심각도**: 보통 · **확신**: 확인됨(QA-T7) · **관련**: FR-08, FR-05, NFR-01

- **실제 결과**: 파일 `R&amp;D 회의.md`, 목록 제목 "R&amp;D 회의", 파일 내용 `R&amp;D 회의`. `a < b`는 `a &lt; b`, 빈 줄은 `&nbsp;`로 저장된다. 글자 그대로의 `*별*`, `[ ]`는 `\*별\*`, `\[ \]`로 저장되어 목록 제목에 역슬래시가 보인다

## 8. 결함이 아닌 관찰
- **외부 수정 덮어쓰기**: 입력 중 다른 프로그램이 같은 파일을 고치면 내 저장이 그 수정을 알림 없이 덮어쓴다(QA-S7). PRD 8장에서 v0.1 정책으로 정한 동작이라 결함으로 보지 않았다. 충돌 알림은 백로그에 있다
- **개발 문서와 코드 차이**: `lib.rs:113` 주석은 "존재 여부·경로 검증"이라고 하지만 `resolve`는 존재 여부를 확인하지 않는다. 없는 스티키 경로로 창이 만들어졌다가 읽기 실패로 바로 닫힌다. 사용자 영향은 없다
- **성능**: 저장할 때마다 감시 이벤트로 `list_tree` 전체를 다시 읽는다. 500개 기준 약 11ms라 v0.1 목표(수백 개)에는 문제없다. 수천 개 이상이면 다시 측정해야 한다
- **"메모" 자동 생성 조건(TC-06)**: `.md`가 없고 하위 폴더도 없으면 PDF 등 다른 파일이 있어도 "빈 폴더"로 본다. PM 확인이 필요하다
