> **대표 결정 (2026-11-08)**: 공개 + MIT. 첫 커밋을 고쳐 로컬 경로를 히스토리에서 지운다. 한 줄 소개는 A안으로 한다. 업데이트 알림은 넣지 않는다(앱은 인터넷에 연결하지 않는다). v0.3은 조용한 출시(저장소 공개 + brew 등록)로 하고, 사이트와 넓은 홍보는 v0.4로 미룬다.

## 0. 결론

1. **공개 + MIT를 추천합니다.**
   - 공개하지 않으면 Homebrew로 배포하기 어렵습니다. 비공개 저장소의 릴리스 파일은 인증해야 받을 수 있습니다.
   - 공개 전에 할 일은 세 가지입니다. ① 로컬 경로를 히스토리에서도 지우기 ② LICENSE 추가 ③ Pretendard OFL 원문 넣기
2. **배포는 GitHub Releases(dmg)와 기존 tap의 cask로 합니다.**
   - Mac App Store는 지금 구조로는 올릴 수 없습니다(`macOSPrivateApi: true`).
   - 개발자 계정($99/년)은 일반 Mac 사용자에게 알리기로 할 때 다시 판단합니다.
3. **홍보 사이트는 지금은 필요 없고, README로 충분합니다.**
   - v0.4에서 알릴 때 GitHub Pages 1페이지를 도메인 없이 만듭니다.
   - 핵심 자산은 "스티키로 꺼내기" GIF 하나입니다.
   - 대표의 앱 세 개를 묶은 허브 페이지 하나가 더 효율적일 수 있습니다.
4. **넓게 알리는 일은 v0.4 이후로 미룹니다.**
   - 아직 BUG-35(Dock으로 종료할 때 저장 누락 의심)와 화면 직접 확인 6건이 남아 있습니다. 메모 앱에서는 "글이 사라졌다"는 후기 하나가 가장 큰 손실입니다.
   - 한국 개발자 채널부터 시작합니다. 해외 채널은 영어 UI가 생긴 뒤에 갑니다(지금은 한국어로 고정).
5. **"Apple 메모처럼"은 README 첫 문구에서 빼기를 권합니다.**
   - 법적 위험은 낮아 보입니다(확인 필요).
   - 다만 차이점보다 닮은 점이 먼저 보이는 것이 마케팅상 손해입니다.

## 1. 공개 vs 비공개

| 항목 | 공개 | 비공개 |
|---|---|---|
| 신뢰 | "로컬 전용·추적 없음"을 코드로 증명할 수 있음. 메모 앱에서 가장 강한 근거 | 서명 없는 비공개 앱은 "출처를 알 수 없는 앱"으로 보임 |
| 배포 | cask가 인증 없이 릴리스를 받을 수 있음 | brew 연결이 사실상 어려움 |
| 포트폴리오 | PRD·디자인·QA 문서 이력이 그대로 보임 | 없음 |
| 기여 | 코드 기여는 드물 것으로 예상. 현실적인 이득은 버그 제보 | 없음 |
| 복제 위험 | 수익이 없으므로 손해가 작음. 이름·아이콘은 MIT와 별개로 대표에게 남음(MIT는 상표권을 주지 않음) | 없음 |
| 유지 부담 | 이슈 응대가 생김. README에 "개인 프로젝트, 응답이 늦을 수 있음"을 명시하고, 이슈 템플릿에서 데이터 손실 버그를 우선 | 없음 |

**라이선스**

| 후보 | 판단 |
|---|---|
| **MIT (추천)** | SageBar·md-editor와 통일됨. 의존성이 모두 MIT/Apache/ISC라 충돌이 없음. 가장 짧고 이해하기 쉬움 |
| Apache-2.0 | 특허 조항과 NOTICE 의무가 있음. 개인 앱에서는 실익이 적음 |
| GPL-3.0 | 남이 소스를 닫은 복제판을 내는 것을 막아 줌. 대신 기여 장벽이 생기고 기존 앱과 정책이 어긋남. 대표가 "닫힌 복제판"을 특히 꺼린다면 고려 |

**Pretendard(OFL 1.1) 호환**
- OFL은 다른 소프트웨어와 함께 배포하는 것을 허용합니다. 글꼴만 따로 판매하는 것은 금지입니다. MIT 앱에 넣어도 문제없습니다.
- 조건은 저작권 표시와 OFL 원문이 글꼴과 함께 가는 것입니다. 지금은 THIRD_PARTY_NOTICES에 이름만 있습니다.
- 할 일
  - `node_modules/pretendard/dist/LICENSE.txt`를 `licenses/Pretendard-OFL.txt`로 저장소에 넣고, 앱 번들에도 넣습니다.
  - NOTICES에 "글꼴 파일은 MIT가 아니라 OFL을 따른다"는 문장을 한 줄 넣습니다.

**공개 전 점검**
- 경로 7곳
  - 새 커밋으로 고치면 첫 커밋에 그대로 남습니다.
  - 커밋이 1개이고 아직 비공개이므로, amend 후 force push하는 것이 가장 깨끗합니다.
  - 사용자명에 회사명이 들어 있다는 점도 고려해 주세요.
- 커밋 작성자는 개인 gmail입니다. 공개되면 이 주소가 보입니다(문제는 아님).

## 2. 배포 채널

| 채널 | 판단 | 비용 |
|---|---|---|
| GitHub Releases dmg | **필수.** 모든 채널의 기반 | 릴리스마다 수동 |
| 자체 tap cask(`reentakim/tap/modoit`) | **추천.** sagebar.rb를 본떠 만들고 postflight로 quarantine 제거. `brew upgrade`로 업데이트 | 릴리스마다 version·sha256 갱신 1분 |
| 공식 homebrew/cask | 불가. Homebrew 5.0부터 Gatekeeper를 통과하지 못하는 cask를 2026-09부터 비활성화·거부(2차 출처, 확인 필요) | — |
| Mac App Store | 지금 불가. `macOSPrivateApi: true`는 Tauri 문서상 심사 거절 사유. 샌드박스에서 사용자 폴더에 접근하려면 security-scoped bookmark로 재작업해야 함 | $99 + 큰 개발 비용 |

**서명 없는 배포가 사용자 경험에 주는 영향과 최소 대응**
- **brew 설치**: postflight 덕분에 경고가 뜨지 않습니다(SageBar와 같음).
  - 다만 Homebrew가 서드파티 tap의 quarantine 제거까지 막을지는 확인이 필요합니다.
  - 릴리스 때마다 다른 계정이나 다른 Mac에서 실제로 설치해 시험하세요.
- **dmg 직접 설치**: macOS 15(Sequoia)부터 "우클릭 → 열기" 우회가 없어진 것으로 알고 있습니다(확인 필요).
  - 대신 시스템 설정 > 개인정보 보호 및 보안 > "그래도 열기"를 거쳐야 합니다.
  - SageBar README는 옛 방식으로 안내하고 있으니 두 저장소 모두 고칠 것을 권합니다.
- **README 설치 절**
  - brew를 맨 위에 둡니다.
  - 직접 설치에는 "그래도 열기" 화면 스크린샷 1장과 `xattr` 명령을 넣습니다.
  - "왜 경고가 뜨나요?"에 세 줄로 답합니다: 공증하지 않음, 소스 공개, 직접 빌드 가능.
- **cask**
  - `uninstall quit: "io.github.reentakim.modoit"`를 둡니다.
  - `zap`은 실제 config 경로에 맞춥니다.
  - caveats는 "첫 실행 때 저장 폴더를 고릅니다" 정도면 충분합니다.
- **업데이트 알림은 대표가 결정할 일입니다.**
  - SageBar처럼 GitHub을 확인하게 하면 "네트워크 없음"이라는 주장과 CSP가 바뀝니다.
  - 넣지 않거나, 넣더라도 기본값을 꺼 두기를 권합니다. brew 사용자는 `brew upgrade`로 받습니다.

**Apple 개발자 계정이 가치 있어지는 때(하나라도 해당하면 재검토)**
- 개발자가 아닌 Mac 사용자(맥 커뮤니티)에게 알리기로 했을 때. 일반 사용자는 Sequoia 경고에서 많이 이탈합니다.
- 설치 실패 이슈가 반복될 때
- Homebrew가 서드파티 tap의 우회도 막을 때
- 비용 측면에서는 계정 하나로 SageBar·md-editor·Modoit을 모두 공증할 수 있으므로 연 $99을 세 앱이 나눠 냅니다.

  3. 저장 구조 그림
  4. "수집하는 데이터 없음"

- **자산(우선순위 순)**

## 5. 포지셔닝

**한 줄 소개 후보**
- A (추천, **채택**): "쓴 메모를 그대로 바탕화면에 붙여 두는 Mac 메모 앱. 저장은 내 폴더의 .md 파일로."
- B: "메모가 곧 스티키. 내 폴더에 Markdown으로."
- 영문(나중에): "Notes that stick — any note becomes a desktop sticky, saved as plain Markdown in your own folder."

**주 사용자**
1. 바탕화면에 할 일이나 참고를 붙여 두는 습관이 있는 Mac 사용자. Stickies는 정리가 안 되고, Apple 메모는 화면에 붙일 수 없어 불편한 사람
2. 메모를 파일로 소유하고 싶지만 Obsidian은 과하다고 느끼는 사람. 같은 폴더를 함께 쓸 수 있다는 점을 강조합니다.
3. Notion 손버릇이 있는 한국어 사용자

**대상이 아닌 사용자**는 명시해 기대를 관리합니다.
- 모바일, 동기화, 협업이 필요한 사람
- iCloud Drive 폴더로 부분적으로 보완할 수 있으나 충돌 동작은 확인 필요입니다.

| 경쟁 | 강점 | Modoit이 다른 점 |
|---|---|---|
| Apple 메모 | 무료, iCloud 동기화, 모바일 | 메모를 그대로 스티키로 꺼냄, .md 파일 소유. 약점: 모바일 없음 |
| Stickies | 기본 내장 | 목록·폴더·검색·Markdown이 있음. 스티키와 메모함이 같은 파일 |
| Obsidian | 플러그인, 링크 | 가벼움, 기본 스티키, Notion식 입력. 같은 폴더를 함께 쓸 수 있음 |
| Bear | 세련된 편집 | 내부 DB가 아닌 파일 그대로, 구독 없음 |
| Notion | 블록, 협업 | 계정·클라우드 없음, 같은 단축 입력 |
| Simplenote | 무료 동기화 | 계정 없음, 스티키 |

**"Apple 메모 같은 화면" 표현**
- **상표**
  - 비교 설명에 Apple 제품명을 쓰는 것은 일반적으로 허용되는 지명적 사용으로 보입니다.
  - 다만 앱 이름, 아이콘, 첫 문구에서 Apple과 관련 있는 것처럼 보이면 위험이 커집니다.
  - 지금은 README 두 번째 줄이라 가장 눈에 띄는 자리에 있습니다. 법률 판단이 아니므로 확인 필요입니다.
- **디자인**: 3단 구성은 Mail, Bear 등에서 흔히 쓰는 관례입니다. 아이콘은 Phosphor를 쓰고 앱 아이콘도 다르므로 위험은 낮아 보입니다.
- **마케팅**
  - "Apple 메모 같은"이라는 말은 "그럼 Apple 메모를 쓰지"라는 반응을 부릅니다.
  - 첫 줄은 "익숙한 3단 화면"으로 바꾸고, Apple 메모는 비교표 안에서만 언급하기를 권합니다.
- **이름**: 웹 검색에서는 동명 앱이 보이지 않았습니다. 다만 상표 검색은 아니므로 KIPRIS 확인이 필요합니다.
